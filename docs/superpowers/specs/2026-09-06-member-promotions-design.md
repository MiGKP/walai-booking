# Member Promotions Design

## Problem

Staff cannot see **who saved or used which promo**, or enforce a **per-member cap**. Today `promotions` only has a global `usage_limit` / `usage_count`, and room checkout accepts a typed code (`POST /api/promotions/validate` + `promotion_id` on `room_bookings`). Kayak create has **no** promo path. There is no collect-to-wallet step.

A teammate proposed a MySQL `member_promotions` table plus `is_collectible` / `stackable` / `usage_limit_per_member`. That SQL does not match this Postgres schema, and it mixes **wallet** (collect) with **redemption** (use on a booking) in one unique row.

## Decisions (approved)

| Topic | Choice |
| --- | --- |
| Shape | Wallet table + redemption table (not one unique row that also points at a booking) |
| IDs / SQL | PostgreSQL; `INTEGER` PKs matching `members.member_id` and `promotions.id` |
| Collect | `is_collectible` default **false** so existing type-code checkout keeps working |
| Per member | `usage_limit_per_member` counted from redemption rows |
| Stack | `stackable` default **false**; when true, multiple redemptions on one booking |
| Rooms | Keep `room_bookings.promotion_id` when exactly one code is applied |
| Kayaks | No new `boat_bookings.promotion_id` column; kayak uses redemption rows only |
| Friend SQL | Do **not** apply as written (`member(id)`, `AUTO_INCREMENT`, `room_bookings(id)`) |

## Out of scope

- Combining room and kayak on one booking / one promo
- Changing `discount_type` / min nights / min price / global `usage_limit` math except where noted
- Dropping `room_bookings.promotion_id`
- Promo packages as a separate product (`room_count` / `boat_ticket_count` stay as catalog fields; this spec does not invent a new package engine)

## Architecture

```text
promotions (catalog)
    │
    ├── member_promotions     ← wallet: one row per (member, promo)
    └── booking_promotions    ← ledger: one row per use on a room or kayak header
            ├── room_booking_id XOR boat_booking_id
            └── promotion_id
```

- **Wallet** answers: did this member collect this code? can they still use it?
- **Ledger** answers: which booking consumed it, for how much discount, for refund/audit.
- Global `usage_count` still increments/decrements with ledger rows (see cancel).

### Why not the teammate’s single table

`UNIQUE (member_id, promotion_id)` plus `booking_id` plus `usage_limit_per_member > 1` cannot store every use. `status = used` also collides with multi-use. Splitting wallet vs ledger is the same header/line idea already used for rooms and kayaks.

## Schema

Use `INTEGER GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMPTZ`, and existing FK names.

### `promotions` (alter)

| Column | Type | Default | Notes |
| --- | --- | --- | --- |
| `usage_limit_per_member` | `INTEGER NULL` | `NULL` | `NULL` = no per-member cap (global cap still applies). Must be `>= 1` when set. |
| `is_collectible` | `BOOLEAN NOT NULL` | `FALSE` | `TRUE` = member must have a wallet row in `saved` before apply. |
| `stackable` | `BOOLEAN NOT NULL` | `FALSE` | `TRUE` = this code may sit on a booking with other stackable codes. |

Existing `usage_limit` / `usage_count` remain the **global** cap.

### `member_promotions` (wallet)

| Column | Type | Notes |
| --- | --- | --- |
| `member_promotion_id` | `INTEGER` PK | |
| `member_id` | `INTEGER NOT NULL` | FK → `members(member_id)` `ON DELETE CASCADE` |
| `promotion_id` | `INTEGER NOT NULL` | FK → `promotions(id)` `ON DELETE CASCADE` |
| `status` | `VARCHAR(20) NOT NULL` | `saved` \| `used` \| `expired` |
| `saved_at` | `TIMESTAMPTZ NOT NULL` | Default `NOW()` |
| `used_at` | `TIMESTAMPTZ NULL` | Set when status becomes `used` (no remaining uses) |

Constraints:

- `UNIQUE (member_id, promotion_id)`
- `CHECK (status IN ('saved', 'used', 'expired'))`

**Status meaning (wallet only):**

| Status | Meaning |
| --- | --- |
| `saved` | Collected; remaining uses `> 0` (including never redeemed) |
| `used` | Per-member cap reached (`usage_limit_per_member` redemptions, or 1 if that column is `1`). Unlimited per-member (`NULL`) never goes to `used` from cap. |
| `expired` | Promo inactive or past `end_date` (write on collect/apply/cron; **also treat as expired on read** if catalog says so even if row still `saved`) |

Do **not** put `booking_id` here.

Indexes: `(member_id, status)`, `(promotion_id)`.

### `booking_promotions` (ledger)

| Column | Type | Notes |
| --- | --- | --- |
| `booking_promotion_id` | `INTEGER` PK | |
| `promotion_id` | `INTEGER NOT NULL` | FK → `promotions(id)` |
| `member_id` | `INTEGER NOT NULL` | FK → `members(member_id)` (denormalized for admin lists) |
| `member_promotion_id` | `INTEGER NULL` | FK → `member_promotions`; **required** when `is_collectible`; **null** when typed without collect |
| `room_booking_id` | `INTEGER NULL` | FK → `room_bookings(room_booking_id)` `ON DELETE CASCADE` |
| `boat_booking_id` | `INTEGER NULL` | FK → `boat_bookings(boat_booking_id)` `ON DELETE CASCADE` |
| `discount_amount` | `NUMERIC NOT NULL` | Snapshot for that code on that booking |
| `created_at` | `TIMESTAMPTZ NOT NULL` | Default `NOW()` |

Constraints:

- Exactly one booking:  
  `CHECK ((room_booking_id IS NOT NULL) <> (boat_booking_id IS NOT NULL))`  
  (one of the two is non-null, not both, not neither)
- Same promo once per room header: unique `(room_booking_id, promotion_id)` where `room_booking_id IS NOT NULL`
- Same promo once per kayak header: unique `(boat_booking_id, promotion_id)` where `boat_booking_id IS NOT NULL`

Indexes: `(promotion_id)`, `(member_id)`, `(room_booking_id)`, `(boat_booking_id)`.

### Header `promotion_id` (rooms only)

| Applied codes on that booking | `room_bookings.promotion_id` |
| --- | --- |
| 0 | `NULL` |
| 1 | That `promotions.id` (keeps current dashboards / history) |
| 2+ (stack) | `NULL` — list comes from `booking_promotions` |

Kayak headers do not get a new promo column.

## Apply / discount rules

Shared helper used by room create, kayak create, and `POST /validate`.

Input: ordered list of promo ids (or a single legacy `promotion_id`).

1. Load catalog rows; all must be `is_active`, in date window, and `usage_count < usage_limit` (if limit set).
2. If `is_collectible`: member must have wallet row `status = 'saved'` for that promo.
3. Count this member’s existing ledger rows for that promo. Reject if `usage_limit_per_member` is set and `count >= limit`.
4. **Stack:** if more than one id:
   - Reject unless **every** promo has `stackable = true`.
   - Reject duplicate ids in the same request.
5. **Math:** start from booking subtotal. Apply codes **in request order**. Each percent/fixed discount uses the **remaining** total (same percent/fixed/`max_discount`/`min_nights`/`min_price` rules as `applyPromotionDiscount` today). `min_nights` applies to room nights; kayak validate uses `nights = 0` or omit min-nights check when nights not applicable — **kayak ignores `min_nights`**, still honors `min_price` against kayak subtotal.
6. Persist: one `booking_promotions` row per code with that code’s `discount_amount`. Bump `promotions.usage_count` by 1 per row. Refresh wallet status (`used` if cap reached; set `used_at`).
7. Set `room_bookings.promotion_id` per the table above.

### Cancel / reject

If header becomes `cancelled` or `rejected` **before** `approved`:

- Delete that booking’s `booking_promotions` rows (or they cascade if we delete the header; prefer **explicit delete + decrement** in the same transaction as status update so `usage_count` stays correct even when the header is kept).
- `usage_count = GREATEST(usage_count - 1, 0)` per removed row.
- Recompute wallet: if under per-member cap, set `saved` and clear `used_at`.

If already `approved` (or later `checked_out`): **do not** restore quota. Ledger stays for audit.

Today create bumps `usage_count` and cancel never decrements; this spec **fixes pending/paid cancel-reject** as part of the ledger.

## API

Keep `{ success, message?, data? }`. Validate with express-validator. Auth: JWT customer for wallet; `admin` + `room_staff` for admin lists (same as current promo admin).

| Method | Path | Who | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/promotions/:id/collect` | customer | Insert wallet `saved`. Idempotent if already `saved`. 409 if `used`/`expired` or promo not collectible/not active. |
| `DELETE` | `/api/promotions/:id/collect` | customer | Remove wallet row only if **no** ledger rows for that pair. 400 if already redeemed. |
| `GET` | `/api/promotions/mine` | customer | Wallet + remaining uses + catalog fields needed for UI. |
| `GET` | `/api/promotions/:id/redemptions` | admin, room_staff | Ledger for that promo: member, booking type, booking id, status of header, `discount_amount`, `created_at`. Also return wallet counts (saved/used/expired). |
| `POST` | `/api/promotions/validate` | existing; if `Authorization` present, enforce collect + per-member cap | Body may add `promotion_ids: number[]` for stack preview. Response includes `discount_amount` total and per-code breakdown. |
| `POST` | `/api/bookings` (rooms) | customer | Accept `promotion_id` **or** `promotion_ids[]`. Same apply helper. |
| `POST` | kayak create | customer | Same `promotion_id` / `promotion_ids[]`. |

Admin create/update promotion: persist the three new columns. Default collectible/stackable false.

Errors (Thai `message`, no stack):

- ต้องเก็บโค้ดนี้ก่อนใช้
- ใช้โค้ดนี้ครบจำนวนครั้งแล้ว
- โค้ดนี้ใช้ร่วมกับโปรโมชั่นอื่นไม่ได้
- โปรโมชั่นหมดอายุแล้ว / โควต้าเต็มแล้ว (global)

## UI

Thai copy. Tokens: forest / cream / existing admin promo page and `RoomCartPanel`.

### Customer

- Room cart: keep typing a code. If validate says collectible and not in wallet, show **เก็บโค้ด** then re-validate. If `stackable`, allow adding another code; otherwise one field as today.
- Kayak checkout: same apply/collect pattern (no kayak promo UI today — add it).
- Optional compact **โค้ดของฉัน** on dashboard/history: list `GET /mine` (saved vs used). No new marketing site required.

### Admin / room staff (`/admin/promotions`)

- Form fields: จำกัดต่อสมาชิก, ต้องเก็บก่อนใช้, ใช้ร่วมโค้ดอื่นได้.
- Per-promo **ผู้ใช้ / ประวัติ** panel from `GET /:id/redemptions` — this is the “เช็คโปรโมชั่น” surface.

## Data flow (happy path)

**Collectible**

1. Customer collects → `member_promotions.status = saved`.
2. Checkout sends promo id(s).
3. Helper checks wallet + caps + stack rules; writes `booking_promotions`; updates `usage_count` and wallet `used` if capped.

**Not collectible (current WELCOME10-style)**

1. Customer types code (no wallet required).
2. Ledger row with `member_promotion_id` null.
3. Optional: do **not** auto-insert wallet (keeps “collect” meaningful). Admin still sees the ledger.

## Testing

- SQL: unique wallet pair; xor booking FKs; cannot insert two of the same promo on one room header.
- Collect twice → one row.
- Collectible apply without wallet → 400.
- Per-member limit 1: second booking rejected; after pending cancel, second booking allowed and `usage_count` restored.
- Two non-stackable codes → 400; two stackable → remaining-total math.
- Kayak create with one promo writes `boat_booking_id` ledger only.
- Room single promo still sets `room_bookings.promotion_id`.
